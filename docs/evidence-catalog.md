## 1. 데이터가 어떻게 정리되어 있는가

### 1.1 저장 위치 — "정의는 코드에 인라인, 목록은 없음"

증거는 별도 카탈로그 파일 없이, **각 씬/상호작용의 대사 트리 안에 직접** 정의되어 있다.

| 소스 | 파일 | 건수 | 형태 |
|---|---|---|---|
| 본편 대사 씬 | `dev/dialogueData.js` | 49건 | `{type:'addEvidence', evidence:{...}}` 이펙트 |
| 탐색 허브 상호작용 | `dev/data/interactionDefs.js` | 6건 | 동일 이펙트, 자유 탐색 토픽에 연결 |
| 사진 확대 미니게임 | `dev/minigame-photo-zoom/` | 8건 | 인물 태그 4종(템플릿) + 특수 확대 지점 4종 |
| 타임라인 정리 미니게임 | `dev/minigame-timeline/` | 2건 | `CaseFileState.addEvidence(...)` 직접 호출 |
| 폰 찾기 미니게임 | `dev/minigame-phone-search/` + `dev/caseFileData.js` | 1건 | 전체 미스터리의 시드 증거(열쇠) |
| (참고, 스토리 미연동) | `dev/minigame-item-scan/` | 가변 | 독립형 테스트 도구 — id가 런타임 생성(`special-ability-*`), 카탈로그에서 제외 |

즉 "증거 전체 목록을 한 파일에서 조회할 방법"이 현재는 없고, 이 문서가 그 역할을 대신한다. (이미 `docs/project-review-evidence-itemization.md`에서 같은 문제를 지적하며 아이콘 카탈로그를 별도 테이블로 분리하는 안을 제안한 바 있음 — 증거 *정의* 자체는 그대로 두고 그 위에 얹는 방식.)

### 1.2 아이템 스키마 (`dev/caseFileState.js:75-86` `addEvidence`)

```js
{
  id: 'evidence-xxx',          // 고유 id — 중복 addEvidence는 no-op (dedup)
  code: 'E-001',                // 표시용 코드 (표기 규칙은 씬마다 제각각, §3.1 참고)
  category: 'physical',         // physical(물증) | photo(사진·영상) | testimony(진술) | record(기록) | etc(기타, 기본값)
  title: '...',
  description: '...',
  discoveredLocationText: '...',
  // 자동 부여 기본값:
  discoveredAt: Date.now(),
  status: 'new',                 // 'new' → 열람 시 'reviewed'로 전환, 갱신 시 'updated'
  relatedQuestionIds: [],
  tags: [],
}
```

증거는 `evidenceStages`(재조사로 같은 카드에 단계 추가)와 `testimonyHistory`(진술 수정 이력)라는 **버전 관리용 필드도 함께 지원**하지만, 실제 콘텐츠에서 `updateEvidence`/`addStage`/`reviseTestimony`를 호출하는 곳은 현재 **0건**이다 — 엔진 기능은 만들어져 있는데 아직 어느 증거도 "갱신"된 적이 없다. 지금은 모든 증거가 최초 등록 그대로 고정.

### 1.3 카테고리 5종 (`dev/caseMenu.js:744-745`)

| 값 | 라벨 | 의미 |
|---|---|---|
| `physical` | 물증 | 현장에서 직접 확보한 물리적 흔적 |
| `photo` | 사진·영상 | 촬영/CCTV 이미지 |
| `testimony` | 진술 | 인물의 말 (참/거짓 여부는 이후 뒤집히기도 함) |
| `record` | 기록 | 메일/메시지/장부 등 문서·데이터 |
| `etc` | 기타 | 폴백 기본값 (실제로 명시적으로 쓰인 곳 없음) |

### 1.4 발견한 구조적 이슈

- **id 충돌 1건 (내용이 다름)**: `evidence-k01-not-for-sale`가 `interactionDefs.js`(팸플릿 문구, E-H02)와 `dialogueData.js`(마틴 베일 통화, E-MV1)에 서로 다른 내용으로 같은 id를 씀. `addEvidence`는 id 중복 시 무시하므로, 플레이어가 어느 경로를 먼저 밟느냐에 따라 카드 내용이 달라진다 — 의도된 설계가 아니라 버그성 충돌로 보임.
- **id 재사용 1건 (내용이 같음, 의도된 패턴)**: `evidence-mina-recovered-photo-fragment`가 서로 배타적인 두 선택 분기(1차 심문에서 즉시 복구 vs 최종 심문에서 뒤늦게 복구)에서 각각 등록됨 — 동일 카드이므로 안전.
- **`question-leo-gap` 중복 등록**: 타임라인 미니게임과 `week1-scene-009`가 서로 다른 `linkedEvidenceIds`로 같은 질문 id를 등록 — 미니게임 쪽이 먼저 실행되므로 씬 쪽 등록은 사실상 무효화됨.
- **문서-코드 불일치**: 코드 주석과 `docs/dev-status-week0-week1.md`가 `minigame-exhibition-search/`를 1주차 Phase 2 미니게임으로 여러 차례 언급하지만, 실제로는 저장소에 **해당 폴더가 존재하지 않는다**.
- **2~4주차는 아직 증거 없음**: `week2`~`week4` 관련 씬에는 `addEvidence` 호출이 0건 — 현재 케이스파일 시스템은 0/1주차에만 실제로 연동되어 있다.

## 2. 중요도 판정 기준

스토리 진행에 대한 기여도를 아래 4단계로 표시했다. 판정 근거는 코드에 실제로 존재하는 신호(진입 조건, 심문 라운드의 정답 증거, 추론 사실 연결, "선택 조사" 메뉴 여부, 코드 주석)에 따른 것이다.

| 표시 | 의미 | 판정 근거 |
|---|---|---|
| 🔴 핵심 | 없으면 진행 불가하거나, 사건의 진실을 직접 확정하는 증거 | `hasEvidence` 진입 조건, 거짓말을 깨는 결정적 제시 증거, 최종 리빌 |
| 🟠 중요 | 결정적 증거를 뒷받침하거나 사건의 방향을 바꾸는 단서 | 심문 라운드 보강 증거, `addFact`(추론 사실) 연결, 이후 뒤집히는 진술의 "씨앗" |
| 🟡 보조 | 선택 조사로만 얻을 수 있고 진행에 필수는 아닌 것 | `reexam-menu`/`reexam2-menu` 등 선택형 서브메뉴, 정황 뒷받침용 |
| ⚪ 배경 | 튜토리얼·레드헤링·분위기용, 이후 재참조 없음 | 코드 주석상 "필수 아님" 명시, 또는 하위 로직에서 참조되지 않음 |
